# Reasoning Model 與確定性 Workflow 的風險分析與平衡做法（討論稿）

## 1. 主題、前提與判斷標準

本稿要回答：**當前 workflow 是否追加過多限制，妨礙 Reasoning Model 在任務內調查、判斷與修正方案，或造成不必要的 token 消耗？在主要使用中低階模型的條件下，哪些限制應保留、簡化、條件化或交給程式？**

**主要使用中低階模型是既定前提，不是等待評測後再決定的目標。** 因此不能以「全面升級高階模型」或「刪光程序指引，讓模型自行處理」作為解法。本文的中低階是使用者的部署與成本取向，不是某個固定產品清單；實測時記錄實際模型、版本與可取得設定。中低階模型也可能具推理能力，不將模型層級與是否推理畫上等號。

評估目標是**在既有品質與授權邊界下，降低完成合格需求的總 token 消耗與人工補正負擔**。單次 prompt 變短或呼叫變少都不等於成功；如果因此增加漏步、錯誤設計或返工，總成本可能更高。

本文是根據現行檔案的設計分析，尚未量測各規則的 token 占比，也未證明哪條規則已造成推理退化。「推理受限」在此指可觀察的行為，例如找不到必要資料、為迎合預估檔案清單而繞路、發現 spec 矛盾卻只能反覆派修；不從最終答案推定模型的內部思考過程。

2026-09-10 使用者確認本次重整主題；授權限於討論稿修訂。下列調整是候選建議，不直接更動 command／agent／hook，也不變更已核准的第一輪 T1–T6 順序與門檻。

## 2. 現況判斷：有局部過度負擔，不宜全面解除限制

現有流程同時包含三類規則，處理方式應不同：

| 類型 | 現行例子 | 對中低階模型的平衡方向 |
|---|---|---|
| 授權與驗收邊界 | 人工核准、token 比對、驗收標準、Git 範圍、Reviewer 不改產品碼 | 保留，不能為省 token 移除；必要時改善執行方式 |
| 任務與推理引導 | 單一 task、角色分工、問題澄清、測試要求、回報格式 | 保留清楚的目標與必要步驟；避免過細拆分、資訊不足及重複要求 |
| 機械式協調 | 抄寫固定欄位、重複生成報告、讀寫計數與狀態 | 優先確認是否可減少模型生成或重複上下文；有可靠替代前仍保留保護 |

初步最值得調整的是：Planner 的資料取得不足、JSON／Markdown 重複生成，以及各 task／修正回合重複交接的內容。最需要保留的是授權、驗收證據與明確的 task 邊界。一次一題、task 粒度及重試上限則有利有弊，需要條件與案例才能決定。

這不是「推理模型天生會重排流程」的結論。把明確相依的寫入平行執行、把待確認需求自行補齊，都屬於執行錯誤；不能將它們當成模型正常發揮必須允許的行為。

## 3. 逐項分析現行限制與成本

以下 R1–R11 是本次分析的穩定編號。每項分開說明現況、收益、推理風險、token 來源與候選做法；不把所有額外 token 都視為浪費。

### R1. 單一 task、依序實作與審查

- **現況／目的：** [Development Step 5](../../commands/agent-work-team-develop.md) 依序處理 task，不平行；[Developer](../../agents/agent-work-team-developer.md) 每次只實作一個 task。這有利於範圍控制與定位問題。
- **中低階模型的需要：** 小而完整的任務可避免同時追蹤太多需求；不能僅為減少派工次數，把整個需求一次交出。
- **推理風險：** 若 Planner 把強耦合變更拆得過碎，Developer 可能只完成局部 AC，無法一次處理共同介面。限制是否過強取決於 task 拆法，並非「單一 task」本身一定有害。
- **token 成本：** 每個 task 都有 Developer、Reviewer、報告及 commit 協調；相同 technical_design、模組與測試背景可能反覆輸入或讀取。平行執行不會自動減少總 token，還可能增加整合成本。
- **候選做法／驗證：** 保留依序與單 task，先改善拆分為「可獨立驗收且脈絡完整」的單位；在核准前辨識強耦合工作。比較同一需求不同拆法的總 token、跨 task 修正與整體缺陷，不擅自合併已核准 task 或新增平行派工。

### R2. 只改 task.files，以及發現新事實時的停止條件

- **現況／目的：** [Developer](../../agents/agent-work-team-developer.md) 已允許為可執行性做必要連動修改並解釋；遠超範圍或重大架構不確定時回報 BLOCKED。這不是完全不可越過的檔案白名單。
- **中低階模型的需要：** 具體檔案與 AC 是範圍提示，能抑制順手重構；不應退回只有一句「把功能做好」。
- **推理風險：** 把 Planning 的預估檔案當成不可質疑的設計，可能導致繞路實作或過早停止。若 spec 錯誤，僅要求照 spec 修碼會持續耗費回合。
- **token 成本：** 合理連動被反覆澄清、重新派工，或同一設計缺口被當成 implementation fix。相反地，全面放寬也可能增加無關 diff 與審查成本。
- **候選做法／驗證：** 保留範圍與現有例外，清楚區分「必要連動」「原 spec 缺口」「新增需求」；前者附理由與影響，後兩者走澄清／變更路徑。以合法連動、越權重構、spec 矛盾案例，檢查誤停、越界與重複派修。

### R3. Planner 的調查空間與輸入假設

- **現況／目的：** [Planner](../../agents/agent-work-team-plan-sd.md) 只有 Read／Write，主要讀 BA artifact，並假設所需資訊在輸入檔案裡；需要產出技術設計與具體 task.files。不足時可回 NEEDS_CONTEXT，但沒有明確的專案搜尋安排。
- **中低階模型的需要：** 有範圍的搜尋指引與證據欄位比無限制探索更容易交接；它仍需要知道專案實際有哪些模組，不能用縮短輸入代替事實。
- **推理風險：** 這是最直接的發揮限制之一：模型可能在資訊不足時先定方案，後續只能修補錯誤假設。Read 能讀已知路徑，不代表能有效發現未知路徑。
- **token 成本：** 調查會增加前期工具輸出，卻可能減少猜測、重複實作與後續返工；把調查 token 全部當浪費，會誤判改善方向。
- **候選做法／驗證：** 沿用第一輪 T3 的限定範圍搜尋、事實／假設區分與追加調查理由；保留足夠的模組／測試脈絡，不要求讀完整 repo。用 Q1 與相關缺資料案例比較重用正確性、返工及整個需求總消耗，而非只比 Planner 的單次長度。

### R4. BA 一次一題、摘要確認與 Spec 核准

- **現況／目的：** [Planning Step 3／5](../../commands/agent-work-team.md) 一次問一個問題，先確認需求摘要，再核准 Spec；checkpoint 保存單一 pending 問題。兩個確認點核對的產物不同。
- **中低階模型的需要：** 一題一答有助於根據前一個答案決定下一題，降低多題遺漏；人工核准也是授權邊界，不能等同無效往返。
- **推理風險：** 若每次都詢問已提供的事實，或外部 skill 再啟動相同澄清，才是冗餘。一次一題若被套在所有互不相依的細項，也可能拖長對話；但需實際案例，不能只因工具可多題就認定規則有錯。
- **token 成本：** 多次往返、重播摘要與 checkpoint 寫入。合併問題可能省回合，也可能因部分回答而多出澄清，不能只計訊息數。
- **候選做法／驗證：** 先保留一題一答，避免重問已有明確答案，完成 AC 即進摘要確認；外部 skill 是否重複按實際載入內容檢查。未來若評估分組提問，要先處理問答對應與續接契約，不能直接刪掉限制。量測必要／重複問題、遺漏、使用者補正與 token。

### R5. 反覆讀寫 checkpoint、state 與 retry counter

- **現況／目的：** [Planning](../../commands/agent-work-team.md) 要求 checkpoint 先於 state；[Development](../../commands/agent-work-team-develop.md) 增加 retry 後重讀數值再分流。[enforce-block hook](../../hooks/enforce-block.mjs) 對超限提供補充保護，並非完整流程引擎。
- **中低階模型的需要：** 明確順序及讀磁碟值能降低依對話記憶判斷的風險；有可靠替代前，刪掉這些步驟可能增加狀態錯誤。
- **推理風險：** 模型需同時做技術工作與機械式記帳，增加必須遵循的規則。這主要是協調負擔，不應解釋為模型需要自由變更 stage 常數。
- **token 成本：** Write 參數中的完整 JSON、Read 回傳、重複的路由規則，以及錯誤後修復。腳本在背景執行的時間本身不是模型 token；只有進入模型請求／輸出的內容才計入相應用量。
- **候選做法／驗證：** 後續以受控操作回傳精簡結果，取代模型手動抄寫；維持驗證與恢復能力，不只是把兩次寫入包成一行。比較協調 token、非法狀態及中斷後恢復成功率；不能從最終 JSON 推斷實際寫入順序。

### R6. JSON／Markdown 雙份報告與重複抄寫 task 內容

- **現況／目的：** 多數角色輸出 JSON 與 Markdown；[Developer](../../agents/agent-work-team-developer.md) 要把 task 描述、檔案、AC 原樣帶進兩份報告。這讓報告可獨立閱讀，不需反查 spec。
- **中低階模型的需要：** 固定欄位與範例有助交接；但固定字串複製與排版不需要模型重新判斷，值得優先比較程式產出。
- **推理風險：** 主要不是解題空間受限，而是重複生成可能引入差異，或擠占輸出預算，使疑慮說明過度簡略。
- **token 成本：** 重複生成相同 task／結果內容，每次修正還要更新報告；這是可定位的消耗來源，但目前沒有實測占比。
- **候選做法／驗證：** 保留資料與人類可讀報告，先盤點能由 JSON 無損渲染的部分。Markdown 修正歷史若未進 JSON 必須保留；task-summary 仍是核准當下快照。比較同等資訊完整性下的輸出 token、不一致與人工修正，不能用刪掉必要資訊達成節省。

### R7. 每 task review 與 final review

- **現況／目的：** [Development Step 5／6](../../commands/agent-work-team-develop.md) 每 task 審查後，再對整體 commit range 審查；[Reviewer](../../agents/agent-work-team-reviewer.md) 必須獨立讀 diff。已有 task／final 範圍區別，不是完全相同的兩次工作。
- **中低階模型的需要：** 局部 review 能提早發現問題，final review 能抓跨 task 介面與完整性；直接取消其中一層可能把成本推到後續返工。
- **推理風險：** 若 final 只重述單 task 結論，沒有檢查交互作用，才是低價值重複。Reviewer 缺 BA 或測試脈絡時，可能核准符合 spec 卻不符需求的程式；加長審查也補不了缺失來源。
- **token 成本：** 累積 diff、先前報告與共通背景被重讀。相同內容再次檢查不必然浪費，需確認它是否新增跨 task 發現或驗證必要依賴。
- **候選做法／驗證：** 保留兩層與完整範圍存取，明確區分 task AC／局部品質與 final 的需求覆蓋／整合／回歸；既有 findings 可索引，但不得用 Developer 摘要取代獨立證據。用 Q3／Q4／Q5 比較漏失、重複 findings、審查 token 與返工；不以 token 降低交換漏檢。

### R8. 角色派工、完整背景與固定回覆行數

- **現況／目的：** [Planning](../../commands/agent-work-team.md) 派 PM／Planner，BA 在主線程；Development 每輪提供 task 與 technical_design，review 傳入其範圍所需資料。角色回覆通常限制 10／15 行，完整內容在 artifact。
- **中低階模型的需要：** 明確角色、必要背景、結構範例及簡短回報有助於交接，不宜一律刪掉。輸出行數不等於內部推理量限制。
- **推理風險：** 交接資料太少會反覆 NEEDS_CONTEXT；太多無關歷史則增加理解負擔。過短回覆若未清楚指出 blocker／證據位置，Controller 可能錯誤續行。
- **token 成本：** 角色 prompt、technical_design、被重讀的 artifact，以及為補足遺漏資訊新增的派工。實際上下文繼承、快取與費用取決於 host，不能只從 command 文字推算每次計費。
- **候選做法／驗證：** 保留當前 task 的 AC、相關設計、依賴、測試與未解問題；較長歷史可提供可定位索引及按需讀取。先測「必要背景＋可取證路徑」，不宣稱越短越好，也不要求只輸出結論。比較交接 token、缺資料回合與漏失；外部 skill 的重複只在證明已載入後計入。

### R9. 修正／缺資訊超過兩次即 Blocked

- **現況／目的：** [Development](../../commands/agent-work-team-develop.md) 對 fix_rounds、needs_context_rounds、final_review_fix_rounds 超過 2 時停止；重跑可依目前路由重設計數。這限制 workflow 重派回合，不是模型只能思考或嘗試兩步。
- **中低階模型的需要：** 上限可防止無限派修與成本失控；取消後不一定更有效。
- **推理風險：** 同一錯誤反覆出現、缺資訊、spec 錯誤與每輪有進展，現在未全數分開處理。過早停止會增加人工接手成本，盲目放寬則可能延長無效循環。
- **token 成本：** 全量重派、重讀與重寫報告。缺欄位與真正程式缺陷若都重做整個任務，可能付出不必要成本。
- **候選做法／驗證：** 先分辨格式、資訊、實作與規格問題；格式修正不得重複產品／Git 副作用，token／approval 不一致不能靠改值通過。沿用第一輪 T5 的 spec gap 分流；一般進展式 retry 待設計，不直接放寬上限。量測無效重派、成功前成本、被阻擋案例與人工接手，保留失敗 run。

### R10. 固定階段、核准與 commit 粒度

- **現況／目的：** 需求有摘要、Spec、Development、Knowledge 等確認點；Developer 逐 task／修正 commit，即使選 squash 也到最終核准才合併歷史。階段與紀錄支援審查及續接。
- **中低階模型的需要：** 清楚的完成與停止條件應保留。小改動也不能把未授權行為推定成核准。
- **推理風險：** 對簡單文件修正或 Research 都套同等詳盡的技術產物，可能促使模型填寫沒有價值的內容；是否實際發生要按需求類型觀察。commit 本身不是推理障礙，但會增加拆分與交接責任。
- **token 成本：** 工具呼叫、commit 訊息、固定七項規格及每階段報告。Git 執行不直接等於大量 token；需看生成與回傳內容，不能以 commit 數直接推估用量。
- **候選做法／驗證：** 先讓內容深度與需求相稱、不補造架構；未來差異化流程須另定完成條件，不在本稿取消 gate 或更改 commit_mode。分別比較小修正／一般功能／Research 的協調占比與產物價值，對應既有第 5 輪 N2。

### R11. Knowledge 全量讀取與主題筆記整理

- **現況／目的：** [Knowledge](../../agents/agent-work-team-knowledge.md) 讀取需求與各 task 報告、搜尋 wiki、產出筆記及 Hub／Index。現行已明定不強求五類知識都有內容，且優先更新既有筆記。
- **中低階模型的需要：** 類別、來源與去重規則提供有用引導；不能誤把現有規則描述成必須生成五類筆記。
- **推理風險：** 為滿足形式而硬造知識、過度抽取 Shared，可能偏離需求價值；目前已有避免過度重構的提醒，應先驗證遵循情況。
- **token 成本：** 大需求的全量報告與逐候選搜尋可能較多；但摘要若漏掉關鍵決策，又會降低知識品質。外部 vault 的錯誤也可能有實際修復成本。
- **候選做法／驗證：** 先確實執行現有「無值得記錄則不建主題筆記」，保留 Hub／Index 要求；後續再評估候選索引與按需讀全文。以 Q6 及有重要設計決策的案例，比較 token、漏記、重複筆記與修改範圍，不以空輸出冒充節省。

## 4. 中低階模型下的具體平衡

本稿的建議分類如下，表示討論優先方向，不是立即實作授權：

| 做法 | 對應 | 原因 |
|---|---|---|
| 保留明確邊界與必要引導 | R1／R2／R7／R8／R10 | 單 task、AC、必要脈絡、驗證證據與核准有用途；避免短 prompt 換來更多返工 |
| 優先補足調查與缺口回報 | R2／R3／R7／R9 | 容許取得新事實與指出 spec 錯誤，才能發揮推理；不把自行擴張授權當成彈性 |
| 優先量測重複生成與交接 | R5／R6／R8 | 能定位複製、格式化、狀態記帳成本，較容易分辨哪些沒有增加品質 |
| 條件化探索，先不刪規則 | R1／R4／R9／R10 | task 粒度、問題分組、重試與需求類型差異都涉及取捨，需案例支持 |
| 先落實現有節制規則 | R11 | 已允許不建立無價值主題筆記，不必先新增另一套限制 |

保留對中低階模型有幫助的簡短步驟、必要欄位與一致範例；優先移除同一規則的冗餘重述、無關背景及可無損轉換的重複輸出。中低階主力配置維持不變，先在同一模型上比較 workflow 版本，避免把升級模型的效果誤算成簡化流程的收益。

## 5. 如何確認省下的是浪費，而非必要工作

### 計量單位：完整需求，而非單次回答

從收到需求至既定完成階段，累計 Controller 與所有角色的實際用量，納入修正、重派、續接及失敗嘗試；只比較相同階段範圍。使用同一 fixture／任務，不只挑成功且便宜的 run。

| 指標 | 記錄方式與限制 |
|---|---|
| token 總量 | 累計各呼叫的 input／output；reasoning 或 cached 等細項依 host 回報口徑分列，若已包含在總項不可重複加總；取不到記 unknown |
| 消耗用途 | 區分技術調查／實作／驗證與狀態協調／報告／交接；角色與用途是兩種切面，不把同一呼叫重複計入總量 |
| 重複程度 | 指認重複生成的欄位、重讀檔案與重問資訊；重複不自動等於浪費，要對照驗證目的 |
| 內容與流程品質 | AC 達成、重要問題漏失、無效建議、越界、錯誤續接、缺資料回合與規格誤派修 |
| 人工負擔與時間 | 補正／澄清／接手分鐘、整體時間；與 token 分開報告，不用假設換算率掩蓋人工成本 |
| 費用 | token 不等同費用；只有實際價格／用量口徑可核對時才計費用，缺資料不推估節省金額 |

工具呼叫多只能作為成本線索，不是 token 的替代計量。若無精確用量，可保留文字長度、讀寫次數與重派次數作代理指標，但不得稱為實測 token 或節省百分比。

### 比較方式

1. 先保留改善前版本的真實對話、工具結果、artifact、模型與 host 設定，盤點 R1–R11 可觀察的成本。現有 [quality eval](../../evals/quality/README.md) 及 [recorder](../../evals/quality/record.mjs) 支援部分證據記錄，不等於已有 token 分析器或時序驗證器。
2. 固定主要中低階模型、任務、host 與可取得設定，針對一種調整做前後比較；不能同時換模型、prompt 與案例，再把差異歸因於某條限制。
3. 沿用第一輪已有的案例、次數、評分與門檻；Q1／Q3／Q4／Q5／Q6 可支援部分品質觀察，但不涵蓋 task 拆分、多題澄清或跨檔中斷的全部問題。新增案例、工具記錄或額外執行另定範圍，不暗增第一輪工作。
4. 同時檢查「總消耗下降」和「品質／授權沒有退步」。保留所有 run 與人工補正；不可只比成功 run 平均值，把更多失敗排除。實際接受門檻沿用已核准設計，未涵蓋的比較另行定義。
5. 限制使模型停住時，分辨是正確阻擋、資訊未給足、流程誤判還是模型能力不足；停下來本身不能證明過度限制。追蹤這一類被阻擋案例的後續修復成本。

本稿尚未完成上述量測，因此結論是「哪些地方值得優先調整／驗證」，不是「已證明省下多少 token」或「所有規則都過度」。
